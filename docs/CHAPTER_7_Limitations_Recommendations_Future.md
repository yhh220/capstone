# Chapter 7: Limitations, Recommendations & Future Enhancement

This chapter reflects honestly on the boundaries of what was built. It sets out the limitations of the current system, offers practical recommendations for the business and for any future development team, and describes the enhancements that would make the most natural next steps. Several of these limitations are deliberate scoping decisions already introduced in Section 1.6.3 rather than oversights; they are revisited here in the context of where the system could go next.

## 7.1 Limitations of Current System

The system meets the objectives set out in Section 1.5, but a number of limitations remain. Being clear about them is important both for setting expectations and for guiding future work.

**Table 7.1: Limitations of the current system**

| Limitation | Explanation |
|---|---|
| Payment runs in test mode only | Card, FPX, and GrabPay payments are processed end-to-end through Stripe Checkout, but in **sandbox (test) mode**: the codebase deliberately refuses live keys, so the platform cannot yet collect real revenue — going live requires the business registration and Stripe merchant verification described in Section 1.6.3. Touch 'n Go, ShopeePay, and Boost remain simulated (Stripe Malaysia does not support them), refunds of paid orders are recorded by the system but executed manually, and the owner's "mark paid" action remains for reconciling WhatsApp/in-store sales. |
| Email-only account verification | Account verification uses email OTP rather than SMS OTP, because SMS depends on a paid third-party gateway (Section 1.6.3). Customers who do not use email are therefore harder to onboard through self-service registration. |
| Rule-based chatbot | The chatbot is a rule-based (retrieval-based) chatbot: it answers by matching keywords against a fixed, admin-managed knowledge base of priority-ranked rules, with typo tolerance. This makes it predictable and free of incorrect "made-up" answers (Section 2.2.4), but it cannot interpret genuinely novel or complex free-form questions; when nothing matches, it hands off to WhatsApp rather than attempting to answer. |
| Dependence on an external scheduler | Because the Render hosting plan does not provide a native cron daemon, scheduled tasks (expiring unpaid orders, sending booking reminders) are triggered by an external pinger (cron-job.org) every ten minutes. This introduces a small dependency on a third-party service and a latency of up to ten minutes before a scheduled task runs. |
| Gmail-specific notification routing | Internal staff alerts depend on Gmail-specific behaviour: because the system sends mail as the shop's own Gmail account, self-addressed alerts never appear in that account's inbox (Section 5.14.2), so delivery relies on CC'ing the admin users' own mailboxes and on a one-time, manually configured Gmail filter that labels the alerts. If the shop ever moved its mailbox off Gmail, the plus-alias convention and filter would have to be re-created on the new provider. |
| Hosting-tier constraints | On a low-cost hosting tier the application can spin down when idle and "cold start" on the next request, making the first visit after a quiet period noticeably slower. In practice this is largely mitigated by the external scheduler pings (Section 5.15), which arrive more often than the idle timeout and so keep the instance warm; but the mitigation depends on that third-party pinger, and a cold start can still occur immediately after a deployment or if the pinger fails. This is a property of the deployment environment rather than the application code. |
| No field performance data yet | Because the site is newly deployed and has limited traffic, Google's field Core Web Vitals are not yet available (Section 6.10); performance is currently evidenced by lab data only. |
| No automated browser (E2E) testing | Automated testing is manual plus a server-side PHPUnit suite (Chapter 6). There is no automated browser-level test layer, so client-side JavaScript behaviour is verified by manual re-testing rather than by an automated end-to-end tool. |
| Status page is manually maintained | The storefront, Contact page, and chatbot direct customers to a public Statuspage, but incidents and component states are updated by staff rather than being automatically driven from application monitoring. This avoids publishing a stale in-app health claim, but requires an operational owner to keep the public page current during an incident. |
| Static assets served by the application server | In production, static files (images, scripts, the hero video) are served by PHP's built-in server rather than a dedicated web server, so responses carry no compression or long-lived caching headers and repeat visits re-download unchanged assets. Moving static delivery to a dedicated web server or CDN, with immutable one-year caching for the hashed build assets, is a deployment-level improvement that requires no application code changes. |
| Configurator is enquiry-oriented | The 3D configurator covers a curated set of models and parts and produces a WhatsApp enquiry rather than a directly buildable, priced order, so it is a visualisation and lead-generation tool rather than a full commerce feature. |

None of these limitations prevents the system from fulfilling its intended role as a showroom-and-management platform, but each marks a clear boundary of the current build.

## 7.2 Recommendations

Arising from those limitations, the following recommendations are offered to the business and to any team that continues the project:

1. **Take the payment integration live only when the business is ready to sell online.** The Stripe integration is already complete in test mode; the recommendation is to keep it in test (or demo) mode until the owner decides to accept online payment, then complete Stripe's merchant onboarding and swap in live keys (Section 7.3.1) — a configuration change, not a rebuild.
2. **Consider a paid hosting tier for production use.** Moving off a free/idle-prone tier would remove cold-start delays and, on a plan with a native scheduler, remove the dependency on the external cron pinger, improving both responsiveness and reliability.
3. **Keep the chatbot knowledge base and public status page current.** Because the chatbot is admin-controlled, the simplest ongoing improvement is for staff to expand and refine its keyword answers as new common questions appear (Section 7.3.2), and to post a timely Statuspage incident whenever an important customer-facing service is degraded.
4. **Monitor real-user performance over time.** Once the site accumulates traffic, the field Core Web Vitals in Google Search Console should be reviewed periodically so that real-world performance can be tracked, not just lab scores.
5. **Gather user feedback continuously.** The user-acceptance testing instrument (Section 6.12) can be reused after launch to collect ongoing feedback from real customers and staff, feeding an iterative improvement cycle rather than a one-off evaluation.

## 7.3 Future Enhancement

The system was architected so that the most valuable enhancements can be added without redesigning what already exists. The four below are the most natural next steps.

### 7.3.1 Taking the Payment Gateway Integration Live

The payment gateway integration anticipated by earlier drafts of this project has since been **implemented in sandbox form** (Section 5.6): card, FPX online banking, and GrabPay payments are processed end-to-end through Stripe Checkout in test mode, confirmed by a signature-verified webhook and a server-side success-URL re-verification that both funnel into the same atomic, idempotent settle step, with the original simulation retained behind the owner's `Payment Mode` setting as a deliberate fallback. What remains as future work is therefore no longer building the integration, but **taking it live and broadening its coverage**.

Going live is primarily a business step rather than a technical one: it requires a registered business, a Stripe merchant account passing Stripe's verification (Section 1.6.3), and swapping the test keys for live keys — the codebase intentionally refuses live keys until that decision is made, so the capstone build can never charge real money. Two technical enhancements would follow naturally. First, **local e-wallet coverage**: Stripe Malaysia does not support Touch 'n Go eWallet, ShopeePay, or Boost, which remain simulated; a Malaysian gateway (for example ToyyibPay, Billplz, iPay88, Fiuu, or Curlec by Razorpay) could be added behind the same settle step to cover them, with the choice depending on the transaction fees the shop is willing to bear. Second, **automated refunds**: cancellations of paid orders currently record the refund amount for manual processing (Section 5.6), and a live gateway would allow the calculated refund to be executed through the gateway's refund API in the same guarded action. Once live keys are in place, the existing online shopping mode toggle (Section 5.10.10) can switch the storefront from showroom-only to genuine online selling without further structural change.

### 7.3.2 Expanded Keyword Chatbot Coverage

The chatbot is a rule-based (retrieval-based) chatbot that answers by matching keywords against a fixed, admin-managed knowledge base of priority-ranked rules, with Levenshtein-distance typo tolerance (Section 5.12). It now includes a trilingual system-status answer and Statuspage call-to-action. A practical future enhancement, fully in keeping with this deliberate design, is to widen and sharpen the remaining knowledge base rather than change its nature. This would include logging the questions the chatbot fails to match so that staff can see exactly which real questions need answers added, broadening keyword coverage and typo tolerance, and extending the trilingual answer set as new products and services are introduced. Because the knowledge base stays entirely admin-controlled, these improvements preserve the chatbot's core advantages identified in Section 2.2.4 (predictable, verifiable answers, with no risk of incorrect information and no running cost) while steadily increasing the proportion of questions it can answer directly before handing off to WhatsApp.

### 7.3.3 Progressive Web App (PWA)

The site already ships a web app manifest (`site.webmanifest`), so it is part-way to being a Progressive Web App. Completing the PWA would mean adding a service worker to enable installability (customers could add the storefront to their home screen like a native app), offline caching of key pages, and, most usefully for this business, push notifications for booking reminders and order-status updates, complementing the existing email notifications. This would strengthen the customer relationship on mobile, which is the primary device for this audience (Section 6.10.2), without the cost of building a separate native mobile app.

### 7.3.4 Advanced Analytics & Reporting

The Filament admin panel already surfaces operational data such as revenue and appointment summaries, and the system now captures product ratings, pickup times, as well as orders, bookings, and activity log data. A future enhancement would build on that foundation with deeper analytics and reporting: sales and booking trends over time, most-popular services and products, product-rating trends, pickup demand by day/time, customer-retention and repeat-visit insights, low-stock alerts, and exportable PDF/Excel reports for the owner. Over a longer horizon, this historical data could support simple demand forecasting to help the shop schedule technicians and stock parts ahead of demand, directly addressing the "poor data management" problem identified in Section 1.3.

### 7.3.5 Enhanced 3D Configurator

The interactive 3D configurator (Section 5.4) is one of the storefront's most distinctive features, but its current visual quality and the range of models it offers were constrained by the time available in this project. Building, compressing, and wiring up each 3D model is time-consuming, so the configurator ships with a curated selection rather than the full catalogue, and the rendering deliberately favours fast loading on a mobile connection over maximum realism. The present result is therefore functional but not yet as polished as we would like. Given more development time, we would continue refining it in two directions. First, improving the visual quality of the rendering itself, for example richer lighting, more realistic materials and reflections, and finer model detail, so that the preview looks closer to the finished vehicle. Second, expanding the model library with more vehicles and a wider range of accessory and styling options, so that more of the shop's real products can be previewed in 3D rather than only a representative selection. Because the configurator is already built as a self-contained client-side component that loads its models on demand, adding further models and improving their appearance is largely incremental work rather than a redesign.

## 7.4 Summary

This chapter set out the current system's limitations honestly, ranging from deliberate scope decisions such as keeping the Stripe payment integration in test mode and email-only verification, through architectural trade-offs such as the external scheduler dependency and manually maintained public-status communication, to the boundaries of the keyword chatbot and the absence of automated browser testing. From those limitations it drew practical recommendations and described five natural future enhancements: taking the payment gateway live, wider keyword-chatbot coverage, a full Progressive Web App extending the existing manifest, richer analytics built on data the system already collects, and further development of the 3D configurator. A recurring theme is that the system was designed to be extended: in each case the groundwork already exists, so these enhancements are evolutions of the current architecture rather than rewrites of it.

# Conclusion

This Capstone Project set out to move Win Win Car Audio Auto Accessories from a purely manual, WhatsApp-and-logbook operation toward a structured digital platform, without pushing the business away from the sales model that already works for it. Measured against the objectives defined in Section 1.5, the project achieved what it set out to do.

A **customer-facing website** was delivered that gives the business a credible online presence, showcases products through responsive multi-image galleries and an interactive 3D configurator, offers verified-and-moderated product reviews, scheduled free store pickup, public service-status access, and a trilingual, accessible, dark-mode interface, and channels customer interest toward WhatsApp and the physical store, the business's proven conversion path. An **administrative dashboard** was built with Filament, giving the owner one secure, mobile-friendly place to manage the catalogue and media, brands, reviews, bookings, orders, and pickup rescheduling, and to oversee operations through analytics, an activity audit trail, and error monitoring. **Strong security and account-protection mechanisms** were implemented and tested (honeypot spam protection, progressive login lockout, role-based access control, two-factor authentication, ownership checks, and concurrency-safe transactions), all layered so that the common, realistic attacks are closed without harming the user experience. Finally, the **optional online shopping mode** was delivered, letting the owner run the platform purely as a showroom or switch on a full e-commerce experience — with payments processed through Stripe's sandbox until the business chooses to go live — giving the business complete control over how the system is used.

The system was verified through the two-layer testing approach described in Chapter 6: continuous manual, exploratory testing as the front line, backed by an automated PHPUnit regression suite, together with dedicated security, concurrency, performance, compatibility, and user-acceptance testing. This gives evidence-based confidence that the platform is functionally correct, secure, and safe under concurrent use.

Beyond the software itself, the project demonstrated the value of combining different technical disciplines (modern web development, structured data management, and proactive cybersecurity) into a single coherent, user-centred product, and of doing so as a group. The limitations and future enhancements set out in this chapter show that the platform is not an endpoint but a foundation: built deliberately so that real payment, a broader chatbot knowledge base, a full Progressive Web App, and richer analytics can be added as the business grows. In closing the one clear gap where Win Win Car Audio Auto Accessories had fallen behind every competitor reviewed, namely the complete absence of any web presence, the project delivers immediate value today while leaving room to grow tomorrow.
